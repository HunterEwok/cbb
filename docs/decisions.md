# Architecture decisions

For engineers. Every decision that shapes Copy Beyond Borders, numbered once and never
renumbered: the code, the changelog and the other documents cite them as D-1, D-2 and so on. The
reasons and the details of each are in the [design](design.md) and the
[protocol](protocol.md); this page is the register.

## How a decision is recorded

A decision is recorded when it closes a choice between real options, or when going back on
it would cost a migration. The pull request that makes it:

1. adds a row below with the next free number and the status `accepted`, in one or two
   sentences: what was decided, and the main reason or the option it rules out;
2. explains it where the work is described: a section of the design or the protocol, which
   names the decision (`(D-81)`), with the options considered and the consequences;
3. when it replaces an earlier one, sets that row's status to `replaced by D-81` and moves
   the row, with its text unchanged, to "Replaced decisions" below, so that old references
   still make sense; when it replaces only a part, the row stays with the status
   `partly replaced by D-81`.

A decision is never deleted or reworded. The statuses are `accepted`, `replaced by D-N` and
`partly replaced by D-N`. To read the architecture as it is, read the decisions in force; the
replaced ones are its history. `tools/repocheck` checks the register: every number once, every
`replaced by` row among the replaced decisions and naming a decision that exists.

## Decisions in force

| D-3 | accepted | A group of equal members instead of a central server; any member may be off. |
| D-4 | accepted | Encryption with the project's own TLS and pairing instead of an overlay VPN, which on iOS would conflict with other VPN apps. |
| D-5 | accepted | At home, members find each other on one network; away from home they reach the hub through the group's own tunnel (D-38). |
| D-6 | accepted | Mac and Linux sync automatically; the iPhone uses one button that picks the direction. |
| D-7 | accepted | Console without a desktop: tmux for copy and paste, a root helper for console paste outside tmux. |

| D-9 | accepted | Pairing a computer: code entry with CPace inside TLS 1.3 instead of comparing digits, which a man in the middle can grind. |

| D-12 | accepted | Own mDNS responder on Linux: no Go library publishes a separate name with its own lifetime, answers per interface and sends goodbyes. |
| D-14 | accepted | The hybrid clock never refuses a timestamp and warns about skew measured per connection; events carry their age for the 45-second rule and secret expiry, and local durations count sleep. |
| D-15 | accepted | macOS runs the service as a LaunchDaemon plus a pasteboard LaunchAgent, which avoids the Local Network prompt; installing needs administrator rights. |
| D-16 | accepted | Desktop clipboard in pure Go: Wayland data-control (both protocol variants) and X11 through `jezek/xgb`; no `wl-clipboard`. |
| D-17 | accepted | Console paste injects a single line by default, with control characters removed. |
| D-18 | accepted | Secrets reach only root and the `cbb` group; the control socket enforces it through file permissions. |
| D-21 | accepted | Each member keeps its own clipboard text apart from the group state; `cbb paste`, tmux, the console helper and the iPhone button use it. |
| D-22 | accepted | A secret travels in a hello as a mark without its text, so the group converges on secrets too. |
| D-24 | accepted | Local durations use a clock that counts sleep and ignores wall-clock steps (package `uptime`). |
| D-25 | accepted | The hybrid clock saves a mark 10 seconds ahead before passing the last one, so it never goes back after a crash. |
| D-27 | accepted | The engine remembers secrets for 12 hours; a watcher offering one again without its mark makes no event, a deliberate action makes it a secret again. |
| D-28 | accepted | Two ways in: watchers report changes (no event when nothing really changed), deliberate actions always send and also write the member's own clipboard. |
| D-29 | accepted | Certificates are checked with the local clock, but never earlier than the group CA's start: a clock that is behind does not break the group, an expired certificate is still rejected. |
| D-30 | accepted | Pairing runs inside TLS with self-signed certificates on the new device's side and channel binding (an exporter and both certificates) instead of a separate encryption layer: CPace authenticates the TLS session, and everything after it travels in that session. |
| D-31 | partly replaced by D-80 | The mDNS responder does not probe its names: device IDs are random, `cbb.local` is never renamed, and the group's election decides who holds it; two holders for a moment are harmless, since any Linux member can serve the iPhone. |
| D-32 | accepted | The Mac browses with CBB's own mDNS code instead of the Bonjour API: it shares port 5353 with mDNSResponder, and the service needs no cgo. The cost is a socket of its own on UDP 5353, which the macOS firewall may treat differently (see Open questions). D-12 still holds for Linux. |
| D-33 | accepted | Several equal admin phones: a root CA with path length 1 certifies an admin CA per phone, each key in its own Secure Enclave or StrongBox, instead of one CA key copied between phones or backed up to a cloud. Only the root makes admins; a remaining admin becomes the root with a signed root record. |
| D-34 | accepted | The devices list and revocations are signed records in a set that only grows and spreads through the member protocol; what it says depends on the set alone, so the group converges. Two admins that revoke each other both lose admin rights. |
| D-35 | accepted | Revoking an admin keeps the devices it admitted, listed in the record, so losing a phone never means pairing the computers again. |
| D-36 | accepted | A computer can be an admin of a phone group, with an admin key in a file that the root phone certifies on request, never by default: admitting from a terminal is worth a key outside a Secure Enclave only to a user who asks for it. |
| D-37 | accepted | Windows runs the service as a Windows service plus a clipboard agent in each session, as on the Mac, since a service cannot reach a session's clipboard; the control socket stays an AF_UNIX socket, guarded by the access list of its directory, so the protocol and the client code are the same everywhere. |
| D-38 | accepted | Away from home: a star of WireGuard tunnels to a hub, a member at home, with WireGuard in user space inside `cbb` and the apps and the member TLS inside; no third-party services; a feature that cannot keep the data fully protected is not built. |
| D-39 | partly replaced by D-75 | Homes behind carrier-grade NAT use a forwarder run by the project that holds no keys and routes each packet to its own group's hub only (by WireGuard's `mac1`, so nothing on the wire tells groups apart; if that fails, by a port the group computes from its secret and the hour, never by a fixed port or a request naming the group), with limits per group. On disk it keeps only each group's roots, removals and freezes (so a removed device cannot register as its hub again), never a device's name. The hub registers with its member certificate; changing the hub's WireGuard key on a schedule and cover traffic are options, off by default. The part on disk is replaced by D-75: the hubs register with a credential (D-67). |
| D-40 | partly replaced by D-87 | Blocked networks: AmneziaWG first, then WireGuard inside VLESS with REALITY to the forwarder, so that traffic always stays inside the group's tunnel. |
| D-41 | accepted | (Push refined by D-74.) Phones keep the tunnel inside the app, without a system VPN or push notifications, so the VPN slot stays free and no one else's server is involved. |
| D-42 | accepted | The ESP32 stays on the home network until a mature WireGuard exists for it. |
| D-43 | accepted | A device away from the group joins by SSH, by the user's own VPN, or by a remote invitation: a QR code or a file, never typed, with a one-time guest WireGuard key that reaches only the pairing and a 128-bit secret, and admitted only after the admin confirms the device. The six-digit code never faces the open internet. |
| D-44 | accepted | Computers keep their keys in the TPM or the Secure Enclave where they have one, and otherwise in a file sealed as far as the system allows, shown as such in `cbb status`; keys are renewed on a schedule. |
| D-45 | partly replaced by D-82 | A group starts on the home network only; sync away from home is turned on by the user, at the hub and on each device, and a device whose keys sit in a file needs a separate consent that explains the risk and the measures against it. |
| D-47 | accepted | (Refined by D-70.) Key attestation (TPM, Android) is built as an option, off by default and not used in the project's own setup; it is checked only offline, so no maker's or Apple's server is involved. |
| D-48 | accepted | The ZX Spectrum Next joins through its own Raspberry Pi, which runs the lite member; no device outside the Next takes part, and a Next without a Pi is future research on its own hardware only. |
| D-49 | accepted | No gateway or plain tier: a device too weak for the member protocol joins through hardware of its own or not at all; on Arduino only ESP32 boards (the Nano ESP32 first) are supported, as full lite members. |
| D-50 | partly replaced by D-89 | A device's operating system (`os`) is stated apart from its role, so a Windows PC is shown as Windows; the roles are `full` (every computer with the service, the Mac included), `lite`, `phone` and `iphone`, and the `linux` and `mac` roles are dropped. |
| D-51 | accepted | In a group a computer creates, only the creating computer (the root) and the members it makes admins hold CA keys, through the admin CAs of D-33 under a root with path length 1; any device but the root is removed by a record without a new group, and a lost root is taken over by an admin. |
| D-52 | accepted | Groups made before D-51 are upgraded in place with a `root` record signed by the old group CA key and a revocation of that key; a leftover copy of the old key can break such a group but never take it over. |
| D-54 | accepted | Every admin may paste a text on any member that turned remote paste on (D-59), the target pressing nothing per paste, since a member already trusts its admins; the command is signed by the admin and checked by the target, and the iPhone is a sender only, because iOS allows no input into other apps. |
| D-55 | accepted | Each device has one switch, sync, on by default: off, its clipboard is its own, as without CBB; it stays connected either way, its user turns it off for a while or until turned on, and any admin turns it on or off on any member with a signed command. |
| D-56 | accepted | Images, files and folders sync wherever the platform allows, with formatted text (HTML) last and optional; lite members, the iPhone shortcut, secrets and remote paste stay text only. |
| D-57 | accepted | Large content travels outside the event: the event carries a manifest with SHA-256 hashes, the bytes are fetched in chunks at lower priority than events from any member that has them, and the clipboard is written only when everything has arrived and matches; each device sets its own limit (100 MiB at home, 25 MiB away from home by default, at most 1 GiB), and the receiver's limit decides. |
| D-58 | partly replaced by D-84 | Images and files have the protection of text: member TLS at home, and away from home only the group's tunnel with member TLS inside it; no further layer is needed, since only group members ever hold the plaintext. |
| D-59 | accepted | Remote paste is opt-in on each device, turned on by its own user; Enter and root consoles are off by default and turned on separately; any admin turns remote paste off on any member with a signed command, and the root or an admin phone removes a stolen admin with one action (refines D-54). |
| D-60 | accepted | Only the root and the admin phones remove an admin; any admin, a computer included, freezes another admin computer, which then counts for nothing until the root or an admin phone unfreezes or removes it; nobody freezes the root or an admin phone. Freezing stops a stolen admin at once from any admin device, while the irreversible removal stays with the keys hardest to steal. |
| D-61 | accepted | With sync away from home on, a computer's service reaches beyond the home network only its group's own servers (hub, forwarder, relay, from the group's settings), in the program on every system and in the system's limit on Linux and Windows, which `cbb global` with root or an administrator keeps in step; a hub reached at its own address answers authenticated clients anywhere, which on Linux only the program can confine to its UDP port. |
| D-62 | accepted | The control socket takes only the clipboard and the status; what changes the group (pairing, removing, renaming, admins, takeover, freeze, sync away from home, the holder setting) takes the admin socket, which only root or an administrator reaches, so membership in the `cbb` group no longer gives a program the group's keys to use. |
| D-63 | accepted | A full member publishes itself by mDNS and takes connections on the member port only on networks where it met its group (by the interface's networks and its gateway's link-layer address); elsewhere it only browses, so a laptop in a café is not tracked by its host label and group tag. |
| D-64 | accepted | A group made on a phone has the phone as its hub while the app is open: at home it accepts member connections, from afar it registers with the forwarder over an outgoing connection, and its clients retry often; the app suggests once moving the hub to a computer that is always on, the old hub passing its clients' keys to the new one, and the user may keep the phone as the hub. Everyone has a phone, not everyone a computer, so the phone does what it can until a better device takes over. |
| D-65 | partly replaced by D-96 | A group may have several hubs in an order the user sets; clients keep every hub's offer and use the first that answers, the hubs share the clients' keys, and a lower hub yields to a higher one, so there is one star at a time. Every capable device with sync away from home on is a hub, in a table signed by the root or an admin that all devices share: the user's main hubs first, then devices with keys in hardware, then devices with keys in files where the key level allows them (D-66); the first one online serves. |
| D-66 | partly replaced by D-84 | Who may be the root, an admin or a hub follows the group's key level, which the user picks: proven hardware only (attestation, asking Apple, Google's public lists and some TPM makers, which the guide names; the one exception to D-47, by the user's choice), hardware by the device's own word (the default, so no device is disclosed to anyone outside the group), or files too, each time after a warning. |
| D-67 | accepted | A forwarder and a relay see credentials made for them, not the group's records: the hubs' and the members' key hashes with a version and an expiry, signed by the root or a listed admin, so no device ID, name, system or date leaves the group. |
| D-68 | accepted | A blind relay is for everyone who needs it, not only for those who run their own: the project runs an open one at `cbb.tools`, within limits per group and per network, and a device meets there only after the user agrees to what it learns (who talks to whom, when, how much, and from where). |
| D-69 | accepted | Releases are signed with the project's own keys, never in CI: two offline root keys (on two hardware keys) certify a release key in the Secure Enclave of the owner's Mac, all P-256 in the records' envelope; each release has a signed manifest of its files and a signed channel pointer with an expiry; a program accepts only a version above the highest it has seen; CI builds a draft that is published only after the owner signs; GitHub Releases is the source and `dl.cbb.tools` a mirror, and members pass the signed manifest and archives to each other. |
| D-70 | accepted | Attestation checked without asking anyone (Android chains, a TPM whose maker's certificate is on the chip) marks a key "proven" at the default level too, since nothing leaves the group. The strict level (D-66) also accepts App Attest for Apple devices, noted as weaker because it proves the app and not the key, accepts only Android chains issued through Remote Key Provisioning, and only there asks Intel or AMD for a TPM's certificate. Google's list of revoked attestation keys is fetched by `cbb.tools` once a day and served signed, so no device asks Google. Relocked custom systems such as GrapheneOS count as hardware. |
| D-71 | accepted | Quick actions and remote paste are turned on only on the device itself, never by a command from the network; the device may ask its user at the first request, and grants a right (a polkit rule, a sudoers line) only then, after a prompt that lists it. Turning either off remotely always works. Reboot and shut down are allowed by default only to admins whose key is in hardware, a choice the device's user can change per action. |
| D-72 | accepted | Collections, the user's own sets of devices and their order in the apps, belong to each app installation and never become a group record: arranging needs no admin signature, and no name of a collection reaches a server. |
| D-73 | accepted | The iPhone is not the hub in the background as a Network Extension: App Review allows VPN apps only from organizations, iOS runs one VPN at a time, Apple advises against a listener in a packet tunnel, and the extension has 50 MiB. The phone stays the hub only while its app is open (D-64). |
| D-74 | accepted | Prompt notifications on the iPhone may come through Apple's push, sent by a stateless sender at `cbb.tools` with the content encrypted to the phone's key and opened only on the phone; Apple learns that a push was sent and when, `cbb.tools` the push token, the hub's address and the time, and the user agrees to that before it is used. |
| D-75 | accepted | Servers learn as little as can be kept from them: the forwarder keeps on disk only a hash of each group's tag with the version of its newest credential (D-67), the relay holds pseudonyms rather than device IDs, the credentials' lists are padded, and each device talks to the servers with its own key renewed every 30 days and signed by the root, so a server cannot link a device across renewals. No transparency report or warrant canary: the defence is that the servers hold almost nothing. |
| D-76 | accepted | Official builds are told apart by the release signatures and the provenance attestation, not by the name: "CBB" is used by other, unrelated projects, so the project claims no exclusive right to it. BRAND.md asks builds with changes not to use the icon, `cbb.tools` as their default or an official look, and to take their own name and app identifiers. |
| D-77 | accepted | The text of docs/protocol.md is under CC BY 4.0, so compatible implementations may use any license; the code stays under AGPL-3.0-only. |
| D-78 | accepted | No additional permission for app stores for now: one can be added at any time but not taken back from released versions; whoever needs a store asks for a commercial license. |
| D-79 | accepted | A full member or a lite member on Linux may be installed without root (`rootless`), as the user's own systemd service with its files in the user's home: it says so in its hello and its device record, and it is never the root, an admin or a hub, not even after a warning, since every program of the user can read its keys. The system install stays the default and the advice; on SteamOS it is kept across updates under `/opt` rather than made rootless. |
| D-80 | accepted | Every phone joins through its app, with a key of its own: the way in for an iPhone without the app (the shortcut, its tokens, the name-constrained iPhone CA and the shared address `cbb.local` with its election) is removed now that the app has an Apple developer account, so the group has one kind of trust and every key in it can be revoked by a record. |
| D-81 | accepted | On the ZX Spectrum Next remote paste is on after `.cbb install`, Enter too, unlike every other device (D-59, D-71): the Next holds no secrets, its installer is run by its own user, BASIC's lines need Enter, and the install says so and how to turn it off (`.cbb paste-receive off`, or any admin in the app). |
| D-82 | accepted | Sync away from home is consented to once on each device by its own user, at install, at pairing or in the app, and stays off without that consent; with it the device turns sync away from home on by itself once it is in a group, and the root or an admin may turn it on again there with a signed command or make the device a hub, so no one types a command on each computer. A device that is never a hub or an admin (keys in a file, rootless, a lite member) still goes online at once with the consent and keeps its role. On Linux and Windows the installer and `cbb pair`, which run with root, write the group's servers into the system's limit right away; nothing runs as root for it later, and a server that changes asks for `sudo cbb global allow`. The limits stay: a device whose keys sit in a file consents only after the warning of D-45, the key level decides who may be an admin or a hub (D-66), a rootless install is never a hub (D-79), and a watch still signs only the commands that turn things off. It replaces D-45's turning on "by the user ... on each device"; ruled out: turning it on by default without asking, which would widen every device the moment it joins. |
| D-83 | accepted | A device leaves its group by itself: `cbb leave` on a computer and on the lite member, "Leave the group" in the apps. It deletes the device's keys and the group's files there (the records, the tunnel's keys, the known networks, the cache of images and files, the logs that name the group's devices), keeps the program and its own settings, and turns remote paste and the quick actions off, since they were allowed to the old group's admins; the device then joins this group or another one, with new keys. The group's root leaves only when no other device is left, after handing the group over (`cbb handover`) otherwise. A device that learns it was removed, or whose group file is damaged, offers to leave. The group lists the device until an admin removes it: a member cannot sign its own removal. Ruled out: uninstalling with `--purge` and installing again, which was the only way before. |
| D-84 | accepted | Copies are sealed end to end: the device that copies seals each copy, text, images and files, to every device of the group that reads copies (X-Wing for each, ChaCha20-Poly1305 for the copy) and signs it with its member key, so the members that pass it on, a hub among them, can neither read, change nor forge it; only what passing it on needs stays outside (sender, time, readers, size in steps). A hub is either trusted (the root or an admin, under the key level) or only passes copies on (`forward_only`, no copy sealed to it, no key level), so key levels concern the root and the admins. Rules out keeping hop-by-hop encryption, in which every member in between read the copies. |
| D-85 | accepted | Every device follows one clipboard rule: a copy from another device goes into the clipboard while it is live, for the group's live window after it was copied (one minute by default, 5 seconds to an hour, set by the root or any admin in a signed `copies` record), counted in durations; once it has passed, the copy is gone and the device's own copy of any age is what its button sends. There is no rejoin window and no separate fetch, and a copy from a removed device is dropped even before it is written. |
| D-86 | accepted | The iPhone and Android apps run the Rust core's member (ffi/, docs/core-api.md, "The member") in place of their own Swift and Kotlin nodes: one implementation of the member protocol, the clipboard rule and the button for every phone, as the Aurora app runs it. The apps keep what is theirs: finding the members (Bonjour, NSD) and handing their addresses in, the keys and Face ID or BiometricPrompt, pairing, the records they sign, the tunnel and the relay (whose loopback ports they hand in), and the answers to commands, renewals and tunnel keys, which the member asks of them by its events. |
| D-87 | accepted | The phones run one tunnel, the lite member's in Rust (`ffi/src/tunnel.rs`), for the client, the phone as the hub with its forwarder and invitations, and the blind relay, in place of a Go tunnel bound by gomobile: one WireGuard, AmneziaWG and VLESS for the lite member and every phone, and app builds without Go. The phones reach a forwarder over VLESS with XHTTP behind a web server only; REALITY stays on the Go servers, whose ClientHello rustls cannot hide. |
| D-88 | accepted | The computers run the Rust `cbb` (member/) as their service and command line, on every member; Go stays only in `cbb-helper`, the child it starts over inherited pipes for what needs Go (keys in the TPM, the agent, the peripherals), and in the forwarder's server until it moves (the relay's server is the Rust `cbb-relay`). Go code that moves into the helper's packages takes its tests with it, and what the Rust service does itself is tested there. It replaces D-2 for the service; D-12 and D-32 hold, with the Rust `cbb`'s own mDNS code in place of Go's, and D-38 and D-40 too, WireGuard and AmneziaWG inside the Rust `cbb` and VLESS with REALITY in `cbb-helper`. |
| D-89 | accepted | The roles `full` and `lite` are one role, `member`, with capabilities in its hello, its device record and its pairing Info: `admin` (may hold an admin key, which gives no rights by itself), `dials` (dials other members; of two that dial, the lower device ID does, the other after 30 s) and `hub` (may be chosen as the hub). Computers, Raspberry Pis and routers have all three, the ZX Next's Pi `admin` and `dials`, an ESP32 none; publishing on every network is a local setting. The phone and watch roles stay. Groups whose records name `full` or `lite`, none of them in a release, are set up again. Ruled out: a third role for each new kind of device, and keeping `full` and `lite` as aliases. |
| D-90 | accepted | A device's role says only how it behaves on the network; its rights come from an admin key alone. Any admin with `admit` admits a phone that offers no admin key as a plain member, as it admits a computer; only the root makes a phone an admin and signs the `admins`, `clock` and `root` records. Ruled out: the earlier rule that only the root signs a phone's device record, which kept an admin from adding a phone without an admin key, such as a TV or the Aurora app, when the root phone was away. |
| D-91 | accepted | VLESS has one transport, XHTTP behind the web server of the forwarder's own site: REALITY is gone from the forwarder (`-vless-site`), the Go client and `cbb-helper`, rather than kept for computers alone or written in Rust, which would need a browser's ClientHello that rustls does not make. Nobody used it once `cbb.tools` ran XHTTP, and one transport for every member and phone is one to test and audit. A client refuses an offer without `transport`, which an older forwarder's REALITY made. It replaces the REALITY parts of D-40, D-87 and D-88. |
| D-92 | accepted | Compatibility from 0.6 on: a device of one release works in a group with devices of the release before it (0.7 with 0.6, 0.8 with 0.7), and an update never breaks a group or makes it be set up again. New record types and fields come only with a new `v`, which older devices keep, pass on and answer with a request to update (protocol.md, section 10, "Records of a later version"); CI updates members of the last release to the new build and checks the group survives. Ruled out: no promise before 1.0.0, which 0.5 had; 0.5 groups are still set up again on 0.6. |
| D-93 | accepted | The Go programs (`cbb-helper`, `cbb-forward`) carry none of the Rust core: they run Go's own rules (`internal/authority`, `internal/clip`, `internal/group`), which the interop vectors and the differential run keep byte for byte the same as the core's. Every member's protocol runs in the Rust `cbb` and the phones' core since D-86 and D-88, so the core as WebAssembly under wazero (and through cgo in tests) only cost two builds of every Go program, a code generator at run time and an entitlement on the Mac for it. Ruled out: keeping the WebAssembly core in the helper as a second reading of the records. |
| D-94 | accepted | The Aurora app asks for a PIN of its own before its root or admin key signs, in place of the system's confirmation, which Aurora OS 5.1.5 gives no regular app (its authentication service is outside the app's sandbox, and there is no API for the fingerprint: a probe on the R570E, and Open Mobile Platform's answer of 2026-11-09). The key sits in a second OP-TEE token of the app (the slot "APP"), whose user PIN the user chooses, at least four digits, and the TEE checks; seven wrong PINs lock it for good, since its SO PIN is random and kept nowhere, and the phone then stays a member. The member key stays in the token QCA makes, so sync needs no PIN. The app wipes the PIN once the TEE has it and keeps the token logged in for five minutes after its last use, as long as the iPhone app trusts one Face ID, while it is on the screen; renewals go only then. Ruled out: no confirmation at all, a PIN only the app checks, a PUK to unlock the key, and the routes Open Mobile Platform suggested (a partner agreement as a company, EBS, Gosuslugi, Max), which do not fit a free app without accounts. |
| D-95 | accepted | A phone joins a group with one button and always as a member; the root makes it an admin later from its device page, as it does a computer, with the admin key the phone's hellos offer once it is in the group (made without a prompt; each signature asks). The root refuses a key the records already name for another device or a root. Ruled out: a second button to join as an admin, which made the user decide at the wrong moment, and asking the user to make an admin key on the phone before the root can promote it. |
| D-96 | accepted | Of a group's hubs outside the user's table, the computers that are the root or admins come first, then the phones, then the devices that only pass copies on: a computer stays on and keeps one place for every client, while a phone is a hub only while its app is open and leaves the network when it sleeps, so the clients and the other hubs reached a phone that was often gone (the protocol's "Several hubs"). Ruled out: phones first, the order since D-65. |

## Replaced decisions

Kept so that the code, the changelog and older documents that cite them still make sense.

| ID | Status | Decision |
|---|---|---|
| D-2 | replaced by D-88 | Language: Go, for reliable ARMv6 builds, TLS and networking in the standard library, and development speed. |
| D-10 | replaced by D-80 | The iPhone trusts a separate CA restricted by name constraints; the token is shown only after that trust is in place. |
