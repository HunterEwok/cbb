# The wire format of 0.6

This reference specifies the byte-by-byte encoding of every message, record, statement, command,
grant, credential, card, and copy in Connect Beyond Borders (`cbb`) 0.6. It is written for
implementers and security reviewers. [protocol.md](protocol.md) defines what each object does and
how devices apply it (the member protocol in section 4, pairing in section 6, and the record rules
in section 10); this page defines how each object is encoded on the wire.

The reference implementation lives in the Rust core (`core/`):

- `cbb_core::format`: CBOR profile, envelopes, keys, frames, grants, copies, and TLS key container
- `cbb_core::records`: records and keys statements
- `cbb_core::commands`: commands and orders
- `cbb_core::copies` and `cbb_core::content`: copies, freshness, blobs, and content payloads
- `cbb_core::msg`: message tables and message validation
- `cbb_core::push`: push registrations, push bodies, and push service messages
- `cbb_core::join`: pairing, invitations, waiting requests, and intros
- `cbb_core::blind`: blind server credentials and server cards

In debug builds, `format::print::describe` formats items using the field names in these tables.

This wire format is preliminary: devices interoperate within one release; see
[versions and compatibility](reference/compatibility.md) and D-131 in
[decisions.md](decisions.md). This page uses the same CC BY 4.0 license as
[protocol.md](protocol.md).

**Test vectors.** `testdata/format/` contains deterministic interop vectors generated by
`python3 -I testdata/format/gen.py OUTDIR` using fixed test keys and RFC 6979 signatures. The Rust
core verifies every vector, and `testdata/format/check` is an independent Go reader that shares no
code with the Rust core. Each vector carries a verdict of `take` (accept and apply), `hold` (valid
encoding, store and relay unchanged, do not apply), or `refuse` with the name of the violated rule.
Rule names throughout this page match those vector rule names. The message tables in this document
match `msg::tables`, `msg::member`, `msg::wave4`, and `cbb_core::push`, which the vector tables
(`messages3.json`, `messages5.json`, `wave4.json`, `push.json`) duplicate and tests verify for
equality.

## 1. The CBOR profile

Every message, record, statement, command, grant, credential, card, and copy header is a single
CBOR data item ([RFC 8949](https://www.rfc-editor.org/rfc/rfc8949)) that conforms to the strict
profile implemented by `cbb_core::format::cbor`.

| Rule | Requirement |
|---|---|
| `cbor/negative`, `cbor/tag`, `cbor/simple` | Allow only major types 0 (unsigned integer), 2 (byte string), 3 (text string), 4 (array), and 5 (map). Refuse negative integers, tags, floats, and simple values (`false`, `true`, `null`, `undefined`, break). Represent a *flag* as the unsigned integer `1`, present only when set. |
| `cbor/indefinite`, `cbor/reserved` | Require definite lengths. Refuse additional information values 28 through 31. |
| `cbor/shortest` | Encode every integer, length, and element count in its shortest form (RFC 8949, section 4.2.1). |
| `cbor/int-range` | Restrict unsigned integers to `0` through `2^63 − 1`, so every platform holds them in a signed 64-bit integer. |
| `cbor/map-key` | Restrict map keys to unsigned integers from `0` through `65535`. |
| `cbor/map-order` | Order map keys strictly increasing (no duplicate keys). For shortest-form unsigned integers, this equals the deterministic bytewise order of RFC 8949. |
| `cbor/utf8` | Require valid UTF-8 per RFC 3629: no overlong forms, no surrogates, and no code points above `U+10FFFF`. Control-character rules are defined per field. |
| `cbor/depth` | Limit container (array and map) nesting to a depth of 8. |
| `cbor/count` | Limit any array or map to at most 65 535 elements; individual field rows are typically stricter. |
| `cbor/trailing`, `cbor/truncated` | Require the input bytes to contain exactly one complete CBOR item with no trailing bytes. |

These rules give every value a single canonical encoding: re-encoding a decoded value produces the
exact input bytes. Writers sort map keys by numeric key value.

**Fields.** Every object in this specification is a CBOR map keyed by field number. Each table row
specifies the field number, CBOR type, whether the field is required, allowed values, and default
value. Two general rules apply to every object:

- `form/default`: Omit any optional field whose value equals its row's default; readers refuse an
  object that encodes a default value explicitly. Omit empty optional arrays, maps, byte strings,
  and text strings in the same way. Always encode required fields, including `0` when the row
  allows `0`.
- `form/type`: Refuse an object if a field has the wrong CBOR type or falls outside its row's
  range. Vectors name these rules by object and field, such as `records/<type>/<field>` or
  `commands/<field>`.

**Sets and unique lists.** An array designated as a *set* contains each element at most once,
sorted strictly increasing in bytewise order of each element's canonical CBOR encoding (for an
array of arrays, sorted by the canonical encoding of each element's first item). An array
designated as *once* contains each element at most once in sender-chosen order.

**Hidden characters.** Hidden characters are code points `U+0000`–`U+001F`, `U+007F`–`U+009F`,
`U+2028`–`U+202E`, and `U+2066`–`U+2069` (`format::is_hidden`). Rows stating "no hidden character"
refuse text containing any of these code points; the debug printer escapes them as `\uXXXX`.

## 2. Common values

| Value | Encoding |
|---|---|
| **Key** | Array `[alg, pub]`, where `alg` is an unsigned integer from the algorithm registry (section 14) and `pub` is a byte string of the length defined for `alg` (`keys/shape`, `keys/es256`, `keys/xwing`, `keys/x25519`, `keys/slh-dsa`). |
| **Key hash** | `SHA-256` of a Key's canonical CBOR encoding (32 bytes). Records, commands, grants, beacons, and statements identify signers by key hash. |
| **Device ID** | First 16 bytes of the key hash of the device's member key, binding each device ID to its key. |
| **Group ID** | First 16 bytes of `SHA-256("cbb group v3" ‖ 0x00 ‖ first_root_key ‖ recovery_es256_key ‖ recovery_slh_dsa_key)`, where each key is its canonical CBOR encoding. A mismatched recovery key produces a different Group ID. |
| **Record ID**, statement ID, credential ID | `SHA-256` of the signed object's canonical body bytes (32 bytes); excludes signatures. |
| **Copy ID**, command ID, invitation ID | 16 random bytes. An invitation ID must not be all zero. |
| **Time** | Unsigned integer, Unix milliseconds. Used for display and by devices with clocks; record evaluation rules do not read timestamps. |
| **Duration** | Unsigned integer, milliseconds. |
| **Hybrid time** | Array `[wall_ms, logical]`, both unsigned integers, with `logical` ≤ `2^32 − 1` and `wall_ms` ≤ `253402300799999` (year 9999). `[0, 0]` is refused. |
| **Address** (`addr`) | Text `host:port` with a numeric IP address: IPv4, or bracketed IPv6 without a zone identifier, flow label, or IPv4-mapped form. |

**Algorithms** (registry in section 14):

| `alg` | Algorithm | `pub` | Signature or ciphertext |
|---|---|---|---|
| 1 | ES256: ECDSA P-256 with SHA-256 | 65 bytes, uncompressed point (`0x04 ‖ X ‖ Y`) on curve P-256 | 64-byte signature `r ‖ s`, big-endian, `1 ≤ r < n`, `1 ≤ s ≤ (n − 1)/2` (low S) |
| 2 | X-Wing KEM | 1216 bytes | 1120-byte encapsulated key |
| 3 | X25519 (WireGuard) | 32 bytes | None |
| 4 | SLH-DSA-SHA2-128s (FIPS 205) | 32 bytes | 7856-byte signature; used only as the recovery key's second half, never as a record's primary signer |

Every primary signing key is ES256 so hardware key stores (Secure Enclave, TPM, Android Keystore)
can sign directly. Where a record or statement carries a key of an unknown `alg` in a position that
expects a signing key, a reader holds the object as it holds an unknown critical field (section
3.3). A reader cannot verify a primary signer of an unknown `alg` and refuses the object.

## 3. Signed objects

### 3.1 The envelope

```
envelope = [ body: bytes, sig: bytes ]                 ; one signer
         / [ body: bytes, sig: bytes, sig2: bytes ]    ; with a second signature
```

- `body` is the canonical CBOR encoding of the object's map wrapped in a byte string, so devices
  sign and relay the exact bytes unchanged. `body` must conform to the CBOR profile.
- `sig` is the ES256 signature by the body's `signer` (field 3) over the signed message
  `label ‖ 0x00 ‖ data`, using the label for the object's kind (section 14). With one signature,
  `data` is `body`. With a second signature, `data` is `body ‖ SHA-256(sig2)`, binding the second
  signature under the first. Distinct labels prevent cross-kind signature replay.
- `sig2` is present if and only if the body contains `signer2` (field 8), the 32-byte key hash of a
  second key. `sig2` is at most 8192 bytes, or at most 32 KiB for a recovery head (record type 13)
  (`env/sig2`); its exact length depends on its algorithm. Readers apply statements, commands,
  grants, credentials, cards, and beacons on the first signature alone while retaining `sig2` to
  relay unchanged; a recovery head requires both recovery key signatures to verify (section 4.8).
  If `sig` fails verification over `body ‖ SHA-256(sig2)` on an envelope carrying `sig2`, the
  envelope is refused as `env/damaged`.
- `env/shape` refuses envelopes with any element count other than 2 or 3, non-byte `body` or
  signature elements, or mismatched `sig2` and `signer2` presence. `sig/size`, `sig/range`,
  `sig/low-s`, and `sig/verify` identify wrong signature length, out-of-range `r` or `s`, high `s`,
  and verification failure.
- Receivers validate in strict order:
  1. Check `body` length against the kind's ceiling (`env/size`, section 13).
  2. Check the CBOR profile on the envelope and on `body`.
  3. Check the body's fields against their table rows.
  4. Verify the signature.
  5. Apply the semantic rules for the object.

  An object that fails any step stops before the next, so no signature is verified over bytes
  another reader rejects, and no record is stored by ID before its signature verifies.

### 3.2 Fields every signed body has

| # | Field | Type | Meaning |
|---|---|---|---|
| 0 | | | Unused in signed bodies |
| 1 | `type` | uint | Object type within its kind |
| 2 | `group` | bytes 16 | Group ID; in `hubs` and `members` credentials, the period tag |
| 3 | `signer` | bytes 32, or Key | Signer's key hash; in server credentials and server cards, the signer's Key itself because servers do not hold group records |
| 4 | number | uint | Signer's increasing sequence number for the kind: record `seq`, statement `epoch`, command `n`, grant `counter`, credential or card `version`, beacon `n` |
| 5 | `prev` | bytes 32 | Records only: ID of the signer's record with `seq − 1`; absent when `seq` is `1` |
| 6 | `time_ms` | Time | Signer's clock timestamp, for display (required on commands and beacons) |
| 7 | `expires_ms` | Time | Commands, credentials, and server cards only |
| 8 | `signer2` | bytes 32 | Key hash of the second signer (section 3.1) |
| 9 | | | Reserved for a future common field |
| 10–255 | | | Type-specific fields: critical zone |
| 256–65535 | | | Optional zone |

### 3.3 Two zones

- **Critical zone (keys 0 to 255).** If a reader encounters an undefined key in this range for the
  object's kind and type, an unknown `type`, or a Key with an unknown `alg` in a signing-key
  position, it **holds** a record or keys statement: it verifies the signature normally, stores the
  object, relays it unchanged during sync, and does not apply it. The evaluated state records up to
  16 held records so apps can prompt the user to update. A command, grant, credential, server card,
  or beacon containing an unknown critical field is refused (`form/critical`): commands are not
  stored, and leaves and servers must understand everything they accept.
- **Optional zone (keys 256 to 65535).** Readers skip unknown keys in this range while still
  enforcing the CBOR profile on their values; the signature covers them.
- Writers emit `revoke`, `freeze`, `resolve`, and recovery head records using only the fields
  defined in this specification, without extra critical fields, so every version can apply them.
  Writers refuse to sign these types with additional critical fields.
- `min_rules` in `settings` (section 4.4) specifies the lowest rules version allowed to handle group
  secrets. This specification defines rules version **1** (`records::RULES_VERSION`). A device whose
  rules version is below `min_rules` does not expose secrets (it opens a copy's content only to
  check whether it is marked secret, then drops it), continues syncing all other data, and prompts
  the user to update.

## 4. Records

Label: `cbb record v3`. A record uses the envelope of section 3.1 with common fields 1 through 6 of
section 3.2. `seq` ranges from `1` to `2^31 − 1` (`records/seq`), and `prev` is present if and only
if `seq > 1` (`records/prev`). The body ceiling is 16 KiB, or 256 KiB for a `checkpoint`. Signing
authority and state evaluation rules are defined in [protocol.md](protocol.md), section 10,
"Records in 0.6".

| `type` | Name | Section |
|---|---|---|
| 1 | `device` | 4.1 |
| 2 | `revoke` | 4.2 |
| 3 | `freeze` | 4.2 |
| 4 | `thaw` | 4.3 |
| 6 | `resolve` | 4.3 |
| 7 | `settings` | 4.4 |
| 8 | `copies` | 4.5 |
| 9 | `checkpoint` | 4.6 |
| 10 | `hubs` | 4.7 |
| 13 | recovery head | 4.8 |
| 14 | `ack` | 4.7 |

Types 5, 11, and 12 are retired: records of those types are refused (`records/retired`), and those
numbers are not reused. Any other unknown type number holds the record.

**`seen` lists.** Several record types carry a `seen` list: an array of `[key_hash: bytes 32, seq:
uint ≥ 1, record_id: bytes 32]` entries, forming a set by `key_hash`, with at most 1024 entries and
`seq ≤ 2^31 − 1`. Each entry names the head of a signer's chain held by the author: a record from
that signer at or below `seq` counts as seen only if it lies on the `prev` chain ending at
`record_id`, and an unlisted signer counts as seen at `0` (`records/<type>/seen`).

### 4.8 The recovery head (13)

A recovery head changes the group's root key. The group's recovery key signs it with both halves:
its ES256 half as `signer` and its SLH-DSA-SHA2-128s half as `signer2`.

| # | Field | Type | Needed | Values |
|---|---|---|---|---|
| 8 | `signer2` | bytes 32 | yes | Key hash of the recovery key's SLH-DSA half; must differ from `signer` |
| 10 | `root` | Key | yes | New root key (ES256); must not equal either half of the recovery key (`records/recovery/root`) |
| 11 | `list` | bytes 32 | yes | Hash of the recovery list accompanying this head |
| 12 | `from` | uint | no | `seq` at which the new root's records as root begin (`1` to `2^31 − 1`); absent for a fresh key (default `0`) (`records/recovery/from`) |
| 13 | `first` | bytes 32 | yes | Record ID of the new root's first checkpoint, signed before the recovery head |

`seq` ranges from `1` to `64` (`records/recovery/seq`). The **recovery list** is a CBOR array of 0
to 1536 record IDs from earlier roots, forming a set (`records/list`), identifying records that
remain kept. It travels alongside its head in field 3 of message `records`, and its hash is
`SHA-256("cbb recovery list v3" ‖ 0x00 ‖ list_bytes)`. Bytes matching the hash that fail to decode
as a valid list are treated as the empty list. A head's first checkpoint is subject to the standard
256 KiB checkpoint body ceiling.

### 4.9 The set digest

Members compare record sets by record ID. The **set digest** is
`SHA-256("cbb set v3" ‖ 0x00 ‖ sorted_record_ids)`, where `sorted_record_ids` is the concatenation
of every held record ID sorted bytewise. Senders transmit records in dependency order, starting
with root records; receivers discard any record whose signer is unknown without storing it.

## 5. The keys statement

Label: `cbb keys v1`. A keys statement announces the public sealing key to which peers seal copies
and commands for the signing device. Only the device's member key signs it.

| # | Field | Type | Needed | Values |
|---|---|---|---|---|
| 1 | `type` | uint | yes | `1` (`statements/type`) |
| 2 | `group` | bytes 16 | yes | Group ID (`statements/group`) |
| 3 | `signer` | bytes 32 | yes | Key hash of the device's member key (`statements/signer`) |
| 4 | `epoch` | uint | yes | `≥ 1` (`statements/epoch`) |
| 6 | `time_ms` | Time | no | Wall-clock timestamp (`statements/time`); devices without a clock omit it |
| 8 | `signer2` | bytes 32 | no | Key hash of a second signer (`statements/signer2`); applied on the first signature alone |
| 10 | `seal` | Key | yes | `alg` 2 (X-Wing), 1216 bytes (`statements/seal`, `keys/xwing`) |
| 256 | `seals` | array of Keys | no | Optional-zone list of sealing keys for additional algorithms; senders seal to the first recognized key among field 10 and this list |

- The body ceiling is 32 KiB (`env/size`). A type other than `1`, an undefined critical field below
  256 (other than `signer2`), or a `seal` of an unknown `alg` holds the statement. A `seal` of a
  known algorithm other than X-Wing is refused (`keys/xwing`).
- Among verified statements for a device, the highest `epoch` is active. A statement is active only
  while the device has a counting `device` record.
- A device rotates to a new `epoch` once its active statement is 7 days old (by wall clock or
  monotonic uptime) and retains the previous secret key until the new epoch is 7 days old. A sender
  with a clock does not seal to a statement whose `time_ms` is more than 35 days behind its clock.
- Message `keys` (t 7) carries up to 256 statement envelopes per message.

## 6. Commands

Label: `cbb command v3`. Devices accept control actions only through signed commands. Whenever a
command carries orders, the sender seals the orders to the receiver's sealing key so only the
receiver can read them.

|---|---|---|
| 1 | `mode` | `10` `mode`: `1` shared, `2` own |
| 2 | `hub` | `13` `stop`: flag `1`, alone; or at least one of `10` `[endpoint: text, key_hash: bytes 32]` (away endpoint, 1 to 255 bytes without hidden characters, and chosen hub's key hash; a receiver with a different key hash refuses it) and `11` `forwarders`: 1 to 8 `[address: text, pin: bytes 32]` (`address` 1 to 255 bytes without hidden characters, each address `once`). Field 12 is retired and refused (`orders/hub`). An empty orders map is refused. |
| 3 | `paste` | `10` `way`: `1` paste, `2` type; `11` `enter`: flag; `12` `kind`: `1` text, `2` secret, `3` media; `13` `text`: 1 byte to 1 MiB (1 byte to 16 KiB when `way` is `2`); `14` `copy`: Copy ID, used instead of `text` only with `kind` `3` and `way` `1` |
| 4 | `paste-off` | None |
| 5 | `action` | `10` `action`: text, 1 to 32 ASCII characters from `a-z`, `0-9`, `-`, starting with a letter |

| 8 | `mute` | `10` `for_ms`: `1` to `2 592 000 000` (30 days); omit to mute until `unmute` |

| 2 | `group` | bytes 16 | yes | Group ID (`commands/group`) |

  on a type that carries orders, or `sealed` on a type without orders, is refused
  (`commands/sealed`). Missing `epoch` with `sealed`, or `epoch` without `sealed`, is refused

  ceiling.

  during signature verification return `commands/signer` and send no reply. After signature
  verification, receivers check `group`, `to`, commander authority (`commands/signer`), admin
  `commands` bit (`commands/right`), clock window within 60 s if the receiver has a clock
  (`commands/late`), counter (`commands/counter`), grant freshness (`commands/stale`) and nonce
  (`commands/nonce`) on a guarded leaf, and then open and check the orders. Any refusal after
  signature verification sends `result` (t 10) with `status` `2` and the rule name in `reason`.
- Message `command` (t 9) carries the command envelope. Message `nonce` (t 21) delivers a 16-byte
  one-time nonce from a guarded leaf, or requests one when field 2 is omitted.

## 9. Frames and messages

### 9.1 Frames

A frame consists of a 4-byte big-endian length `L` followed by `L` bytes containing one CBOR map in
the profile. Field `0` (`t`) identifies the message type (`frame/message`).

- **The grid.** `L` must be `64`, `256`, `1024`, `4096`, `16384`, or a multiple of `16384`
  (`frame/grid`). When the unpadded message length is not on the grid, the writer adds `pad`
  (field `1`), a byte string of zero bytes (`frame/pad`) sized to reach the smallest grid step that
  fits; a message already on the grid omits `pad`. Frame lengths therefore expose only the grid
  step, not exact record counts or small message types.
- **Limits.** The maximum frame length `L` is:
  - Member connection: 7 MiB (`frame::LIMIT_MEMBER`, `7 340 032` bytes)
  - Pairing connection: 1 MiB (`frame::LIMIT_PAIRING`), except message 67 (`welcome`), which may
    reach the member limit
  - Leaf connection: 16 KiB (`frame::LIMIT_LEAF`), enforced by peers according to the leaf's record
  - Push service connection (`cbb-push/1`): 16 KiB (`push::MAX_SERVICE_FRAME`, `16 384` bytes)

  A length of `0`, off the grid, or over the connection's limit closes the connection.
- **Chunks.** A length word with its high bit (`0x8000_0000`) set marks a binary `chunk` frame
  carrying sealed blob data, sent only in response to `get`. The remaining 31 bits give the payload
  length, followed by:
  - Blob `SHA-256` (32 bytes)
  - Byte offset (8 bytes, big-endian)
  - Data length (4 bytes, big-endian, at most 256 KiB)
  - Data bytes
  - Zero padding up to a multiple of 16 KiB

  Chunk frames bypass the CBOR message parser. Any chunk frame larger than `278 528` bytes closes
  the connection.

**Messages.** Receivers ignore unknown `t` values. Within a recognized message, receivers skip
unlisted fields (messages are unsigned and have no critical/optional zones), allowing future
versions to add messages and fields. Listed fields must match their type and bounds, required
fields must be present, and fields equal to their default must be omitted. Values outside a known
field's range refuse the message, except where treating the field as absent is neutral or stricter
(`msg::later` and `testdata/format/future.json`), never where doing so would grant additional
authority, change operating mode, or alter values shown for user approval.

**Sealed push body.** For every registered `env`, the sealed push body in `push/send` field 6 is
exactly 2972 bytes: `nonce (12 bytes) ‖ ciphertext (2944 bytes) ‖ tag (16 bytes)`
(`pushbody/size`). The sender derives two 32-byte keys from the phone's 32-byte push key `pk`:

- `body_key = HKDF-SHA256(pk, salt empty, info "cbb push body v1")`
- `nonce_key = HKDF-SHA256(pk, salt empty, info "cbb push nonce v1")`
- `ad = "cbb push v1" ‖ 0x00 ‖ seq_be64`
- `nonce = HMAC-SHA256(nonce_key, ad ‖ plaintext)[0..12]`
- `ciphertext ‖ tag = ChaCha20-Poly1305(body_key, nonce, ad, plaintext)`

Because the nonce is derived deterministically from `ad ‖ plaintext`, every member sending the same
notification produces identical ciphertext bytes, letting the push service deduplicate repeats. The
receiver verifies that the received nonce matches `nonce_for(pk, ad, plaintext)` (`pushbody/nonce`)
after opening (`pushbody/open`).

The plaintext is a CBOR map padded with `pad` (field `1`, zero bytes) to exactly 2944 bytes
(`pushbody/pad`); if the unpadded map is already 2944 bytes, `pad` is omitted:

| # | Field | Type | Needed |

| 0 | `kind` | uint ≥ 1 | yes |
| 1 | `pad` | bytes (zeros) | To reach 2944 bytes |
| 2 | `copy` | bytes 1..2944 | `kind` `1` |
| 3 | `id` | bytes 16 | `kind` `2`, `3` |
| 4 | `origin` | bytes 16 | `kind` `2` |
| 5 | `event` | uint ≥ 1 | `kind` `3` |
| 6 | `device` | bytes 16 | |
| 7 | `time_ms` | uint 0..2^63−1 | |

  (`pushbody/age`).
- `kind` `2` (waits): hint that copy `id` from `origin` is waiting.
- `kind` `3` (event): hint of a group event identified by `id` and `event` (`1` joined, `2`

## 10. The copy

### 10.1 Wire form

A copy is a CBOR map:

| # | Field | Type | Needed | Meaning |
|---|---|---|---|---|
| 1 | `hdr` | bytes | yes | Canonical CBOR header map (section 10.2), signed via its hash |
| 2 | `age_ms` | Duration | no | Outside the signature; grows in transit (default `0`; writing `0` returns `form/default`) |
| 3 | `wraps` | array of bytes | yes | One entry per header reader in the same order: either the copy key sealed to that reader (at least 49 bytes; an X-Wing wrap is 1168 bytes), or in a **reduced copy** that wrap's `SHA-256` (32 bytes) |
| 4 | `payload` | bytes | One of 4 or 5 | Sealed content: a padded step of section 10.3 plus its 16-byte tag |
| 5 | `payload_hash` | bytes 32 | One of 4 or 5 | `SHA-256(payload)`, used instead of `payload` in a **mark** (a secret's current copy in `hello`) or a reduced copy |
| 6 | `sig` | bytes 64 | yes | Origin's ES256 signature (section 10.2) |

Exactly one of field 4 or field 5 must be present, and `wraps` must have the same length as header
`readers` (`copy/shape`). Any undefined field below 256 refuses the copy (`form/critical`). A
**reduced copy** (for a leaf or push body) keeps the target device's own wrap intact and replaces
other wraps with their 32-byte `SHA-256` hashes; for a leaf, it keeps `payload` intact only if the
resulting `copy` message fits in 16 KiB, otherwise replacing it with `payload_hash`
(`copy/leaf-frame`).

### 10.2 Header and keys

| # | Field | Type | Needed | Meaning |
|---|---|---|---|---|
| 1 | `id` | bytes 16 | yes | Copy ID |
| 2 | `origin` | bytes 16 | yes | Origin's Device ID |
| 3 | `time` | Hybrid time | yes | Signed hybrid timestamp (`copy/time` if wall time exceeds `253402300799999`) |
| 4 | `readers` | array | yes | 1 to 256 `[device_id, epoch]` entries, a set (`copy/readers`) |
| 5 | `blob` | array | no | `[size, sha256: bytes 32]` of the sealed blob |
| 6 | `commit` | bytes 32 | yes | `HKDF-SHA256(K, salt empty, info "cbb copy commit v2")`: commits to copy key `K` |

Field 7 is reserved and refused (`copy/reuse`); any other undefined field below 256 returns
`form/critical`, and any malformed row returns `copy/shape`.

The origin draws a random 32-byte copy key `K` and computes:

- `h = SHA-256("cbb copy v2" ‖ 0x00 ‖ hdr)`
- `payload_key = HKDF-SHA256(K, salt h, info "cbb copy payload v2")`
- `blob_key = HKDF-SHA256(K, salt empty, info "cbb copy blob v2")` (independent of `h`, which
  commits to the sealed blob's hash, so resealing the copy with the same `K` keeps the blob
  readable)
- `payload = ChaCha20-Poly1305(payload_key, nonce 12 zero bytes, ad h, content)`
- Each wrap: X-Wing HPKE of `K` to the reader's statement key for that epoch, with info
  `cbb seal v1` and associated data `h`
- `W = SHA-256(SHA-256(wrap_0) ‖ ... ‖ SHA-256(wrap_{n-1}))` and `P = SHA-256(payload)`
- `sig = ES256("cbb copy sig v2" ‖ 0x00 ‖ h ‖ W ‖ P)`

A reader decapsulates its wrap (`copy/wrap`), verifies `commit` against `K` before decrypting
anything else (`copy/commit`), and then decrypts `payload` under `h` (`copy/payload`). A leaf can
verify `sig` from a reduced copy alone because `W` and `P` depend only on hashes.

**The blob.** A copy's part bytes are concatenated in manifest order into a single stream, padded
with zero bytes to a multiple of 64 KiB (one segment). Each 64 KiB segment is encrypted with
ChaCha20-Poly1305 under `blob_key`, using nonce `0x00000000 ‖ segment_index_be64` (counting from
`0`) and associated data `"cbb blob" ‖ final_byte`, where `final_byte` is `0x01` for the final
segment and `0x00` for earlier segments to prevent truncation. The sealed blob is the concatenation
of sealed segments (65 552 bytes each); header field `blob` records its total byte length and
`SHA-256`.

### 10.3 Content

Inside `payload` is a CBOR map in the profile. Field `1` (`pad`, zero bytes) pads the canonical
encoding to the smallest step that fits: 1 KiB, 4 KiB, 16 KiB, 64 KiB, 256 KiB, 1 MiB, 2 MiB,
3 MiB, or 4 MiB. When the unpadded encoding already equals a step, `pad` is omitted
(`copy/content-pad`).

| # | Field | Type | Meaning | Default |
|---|---|---|---|---|
| 0 | `type` | uint | `1` text, `2` clipboard media (images, formatted text), `3` files, `4` device state | |
| 1 | `pad` | bytes | Zero bytes | |
| 2 | `flags` | uint, bits | `1` secret (applicable to any type) | `0` |
| 3 | `ttl` | Duration | Copy-specific lifetime: `5 000` to `3 600 000` ms | Group lifetime (section 4.5) |
| 4 | `via` | uint | `1` phone, `2` universal clipboard | Regular copy |
| 5 | `text` | text | Text content (at most 1 MiB for type 1, `clip::MAX_TEXT`), or plain-text alternative beside media or files (at most 256 KiB, `media::MAX_ALT_TEXT`); empty text returns `form/default` | |
| 6 | `manifest` | map | Types 2 and 3: `1` `size` (optional, default `0`), `2` `parts` (1 to 10 000 maps with `1` `type`: `1` png, `2` jpeg, `3` gif, `4` html; `2` `path` text; `3` `dir` flag; `4` `size` optional, default `0`; `5` `sha256` bytes 32). Undefined keys below 256 inside `manifest` or a part return `content/manifest`. | |
| 7 | `data` | bytes | Type 4: device state, 1 B to 4 KiB, containing one CBOR item defined by the device's firmware | |

- A type above `4`, an unknown `flags` bit, or an undefined critical field below 256 marks the
  content **unknown**: devices retain and relay the copy but never write it to a clipboard.
- Type `1` requires `text`. Types `2` and `3` require `manifest` (and only they may carry
  `manifest`). Type `4` requires `data` (only it may carry `data`) and forbids `text`. Content
  rules are `content/type`, `content/flags`, `content/ttl`, `content/via`, `content/text`,
  `content/manifest`, and `content/data`.
- A manifest contains either clipboard media (every part has `type`, each type `once`, at most 8
  parts) or files (every part has `path`). Combined part sizes are at most 1 GiB; each path is at
  most 16 KiB; each path component is at most 765 bytes; all paths combined are at most 2 MiB.
  Every path component must be valid UTF-8, neither `.` nor `..`, free of control characters,
  bidirectional controls, and `/ \ : * ? " < > |`, must not end in a dot or space, must not match
  a Windows reserved device name before its first dot (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`,
  `CONOUT$`, or `COM`/`LPT` followed by a digit `0`–`9` or superscript `¹`/`²`/`³`, ignoring
  trailing spaces before the dot), and must equal its Unicode 15.1 NFC form
  (`core/src/content/unicode.rs`). Two paths that collide under case folding count as duplicates.
  Receivers neither create nor follow symbolic links.

### 10.4 Readers, checks and sealing again

- **Readers.** The origin seals a copy to every device whose `device` record grants `read` (and,
  for a secret, also `secrets` with rules version at least `min_rules`), does not skip the content
  type, is not a `watch`, and holds a counting keys statement. A leaf receives a wrap only if the
  origin is authorized by the leaf's grant: a `reader` for an ordinary leaf, or a `commander` for
  a guarded leaf (`copy/leaf-sender`). Root and admin keys decrypt nothing.
- **Checks.** Every member—including hubs that only relay copies—verifies that the origin is a
  known device with `send` and an unfrozen admin key (`copy/origin`, `copy/send`) and verifies the
  copy signature before relaying it. Copies are identified by `(origin, id)`.
- **Freshness.** A reader with a clock refuses any copy whose signed wall time is more than 5
  minutes (`300 000` ms) ahead of its clock or outside the valid clock range. For age evaluation,
  the clock-skew allowance is `min(5 minutes, ttl / 4)` (5 minutes if the copy has no lifetime),
  and the effective age is `max(age_ms, now − signed_wall − allowance)`. A reader writes no copy
  whose signed time is not strictly after the newest copy written from standing (unrevoked,
  unfrozen) origins—with non-standing origins capped by the newest judged copy from standing
  origins—and never writes the same secret twice.
- **Sealing again** (`reseal`, t 23). Only the copy's origin reseals it, and only when the group is
  not stopped (`reseal/halted`), for a device that was and remains a reader of the copy
  (`reseal/reader`), at the epoch of its active keys statement (`reseal/not-current`), within the
  copy's lifetime (`reseal/expired`), and at most twice per `(asker, copy)` (`reseal/limit`). The
  resealed copy preserves `id`, `origin`, and `time`, lists only the requester in `readers`, and
  has a new header.

### 11.4 The intro (t 8)

Sent first by a peer whose member key the receiver does not yet hold, carrying the chain of records
connecting the peer to the root the receiver holds:

| # | Field | Type | Needed | Meaning |
|---|---|---|---|---|
| 2 | `records` | array of envelopes | yes | At most 32 records totaling at most 16 KiB in dependency order (proving the admitter's authority, then the sender's own record), plus up to 65 recovery heads counted separately (`intro/size`) |
| 3 | `keys` | envelope | no | Sender's keys statement |

The receiver verifies every signature up to its held root before accepting and continuing; any
failure closes the connection without storing anything (`intro/shape`, `intro/record`).

## 12. The key container for TLS

TLS requires a certificate. Every device constructs the same fixed DER template from its P-256
public key alone (`format::container`): 221 bytes total, containing a 195-byte `TBSCertificate`
with the 65-byte uncompressed public point at offset 130.

```
30 81 da                                   Certificate (218)
  30 81 c0                                 TBSCertificate (192)
    a0 03 02 01 02                         version v3
    02 10 <16 bytes>                       serial = SHA-256(point)[0..16], first byte 0x40 | (b & 0x3f)
    30 0a 06 08 2a8648ce3d040302           ecdsa-with-SHA256
    30 0e 31 0c 30 0a 06 03 550403 0c 03 636262            issuer CN "cbb" (UTF8String)
    30 20 17 0d 3730303130313030303030305a                 notBefore 1970-01-01 00:00:00Z (UTCTime)
          18 0f 39393939313233313233353935395a             notAfter 9999-12-31 23:59:59Z (GeneralizedTime)
    30 0e 31 0c 30 0a 06 03 550403 0c 03 636262            subject = issuer
    30 59 30 13 06 07 2a8648ce3d0201 06 08 2a8648ce3d030107   id-ecPublicKey, P-256
          03 42 00 <65-byte uncompressed point>
  30 0a 06 08 2a8648ce3d040302             ecdsa-with-SHA256
  03 09 00 30 06 02 01 01 02 01 01         signature: ECDSA r = 1, s = 1
```

- Deriving the serial number from the key avoids collisions in Apple's keychain, which treats two
  certificates with the same issuer and serial as identical.
- The certificate carries no extensions, no Subject Alternative Name, and no SNI, so the TLS
  handshake reveals neither the device nor the group.
- **Readers** verify the `TBSCertificate` byte-for-byte against the template with the extracted
  public point and derived serial in place, verify that the point lies on P-256, and check its key
  hash against the dialed peer or group records (`container/template`). Readers validate only the
  signature's ASN.1 structure (a `BIT STRING` with 0 unused bits containing a `SEQUENCE` of two
  `INTEGER`s, at most 72 bytes total) and ignore its value; TLS `CertificateVerify` proves key
  possession.
- **Writers** emit the constant signature `r = 1, s = 1`, making the entire container a
  deterministic function of the public key.
- Test vectors live in `testdata/format/container.json`.
